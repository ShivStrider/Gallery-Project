# Decision Log

Format: Problem → Options → Selected → Reason / Trade-offs / Risks / Reversal cost / Validation.

**D1 — Crash reporting.** Firebase Crashlytics (status quo) vs internal-flavor Crashlytics vs remove entirely. → **Remove entirely.** The APK must not hold INTERNET; collection was inverted (debug-on/release-off) so production reporting was dead anyway; removal also un-broke fresh-clone builds (google-services.json). Trade-off: no fleet crash telemetry — accepted for a privacy product; failure state persists locally. Reversal: re-add plugin+dep (~1 day). Validation: merged manifest has no INTERNET; fresh clone builds.

**D2 — Face embedding model.** MobileFaceNet TFLite vs FaceNet-512 vs MediaPipe embedder vs custom. → **MobileFaceNet, 112×112→128-D, cosine — now sourced, converted, and committed.** Weights come from sirius-ai/MobileFaceNet_TF (Apache-2.0, verified against the repo's LICENSE), converted from the published frozen graph with TensorFlow 2.15.1; provenance, both checksums, and the exact conversion command are recorded in `app/src/main/assets/README_MODEL.txt`, and the artifact SHA-256 is pinned via `faceModelSha256` so `verifyFaceModelPresent` gates it. **Correction to the original decision**: this contract was recorded as 512-D, which was never true of this model — the graph emits 128 values, so `EMBEDDING_SIZE` was corrected to 128. The distributability concern is resolved for this artifact: Apache-2.0, upstream-published weights. Reversal: any model is drop-in given a matching `MODEL_INPUT_SIZE`/`EMBEDDING_SIZE` and a re-pinned checksum; a different width requires a full re-scan (embeddings of mixed widths cannot be compared). Still unvalidated: recognition accuracy has not been measured against a labelled dataset.

**D3 — Distribution target.** Play Store now vs sideload now/Play later. → **Sideload-ready first, Play-rigor docs maintained.** (User did not answer; assumption recorded, easily re-prioritized.)

**D4 — Face detection library.** ML Kit bundled (existing) vs MediaPipe vs OpenCV. → **Keep ML Kit** (on-device, proven in codebase, no network). Trade-off: +7 MB APK for the bundled model — correct for privacy.

**D5 — Clustering algorithm.** Online centroid (existing) vs DBSCAN/HAC batch vs hybrid. → **Keep online centroid + merge pass**, add in-memory cache and a review-needed band. Reason: incremental by nature (new photos don't re-cluster the world), simple, already tested; full recluster exists for threshold changes. Trade-offs: order sensitivity, centroid drift — mitigated by merge pass + user corrections. Reversal: `ReclusterUseCase` isolates the algorithm (moderate).

**D6 — Similarity thresholds.** assign 0.60 / merge 0.75 (existing, user-adjustable strictness) with merge > assign invariant. Validation: threshold-band tests + review-needed group absorbs the ambiguous zone.

**D7 — Database.** Room (existing, v3→v4 additive). Never edit shipped migrations.

**D8 — Background processing.** WorkManager foreground dataSync workers (existing pattern) for scan, recluster, and export M1. Consent (M2) is UI-only by OS design.

**D9 — Storage access.** MediaStore-only; no SAF. Destination is app-owned `Pictures/FaceAlbums/` via MediaStore inserts; source deletion via `createDeleteRequest`. SAF folder-picking rejected: adds a permission-persistence maze for no MVP gain. Reversal: SAF destination could be added later behind the same use-case seam.

**D10 — Export method.** Copy→verify(SHA-256+size+readable)→consented delete, per-file Room transaction log, two-phase (background copy / foreground consent), API 30+ gate for Move, copy-only until the destructive suite is green. Alternatives (direct move, rename-based move) rejected: not atomic across volumes, impossible on unowned media under scoped storage.

**D11 — Undo strategy.** Log-driven: copy-mode undo deletes app-owned copies; post-delete move undo restores from verified copies then deletes them. No trash/staging dir (doubles storage, another consent round).

**D12 — Thumbnail caching.** Coil only; no persistent thumbnail store (replaceable derivative data).

**D13 — Dependency injection.** None (manual wiring, existing). Hilt adds build+cognitive cost with no swap-in need at this scale.

**D14 — Supported Android versions.** minSdk 26, target 35 (existing). Move mode 30+. Rationale in `05-safe-export-design.md`.

**D15 — Static analysis.** detekt (CI) + AGP lint; version pinned compatible with Kotlin 1.9.20. ktlint deferred — one formatter/analyzer is enough to start.

**D16 — Kotlin/Compose versions.** Stay on Kotlin 1.9.20 / Compose BOM 2024.02 for MVP: internally consistent, upgrade is churn without user value mid-plan; revisit post-release.

**D17 — Export metadata fidelity.** Exported copies appeared in Google Photos dated the moment of export, scattering a person's album to the top of the timeline. Options: (a) leave it, the EXIF is intact; (b) carry the source's MediaStore timestamps onto the destination row; (c) re-derive dates by parsing EXIF out of the copied bytes. → **(b).** The file bytes were never wrong — the EXIF inside each JPEG is copied verbatim. What was wrong is the MediaStore *row*: both insert paths set only `DISPLAY_NAME`/`MIME_TYPE`/`RELATIVE_PATH`/`IS_PENDING`, so MediaStore stamped `DATE_TAKEN`/`DATE_MODIFIED` itself at insert time, and gallery apps sort on those columns rather than on EXIF. (a) was rejected because the user-visible symptom is real regardless of what the bytes contain; (c) was rejected as strictly more work with more failure modes for the same result, since the source row already holds the values. **Unit trap, load-bearing:** `DATE_TAKEN` is milliseconds since epoch, `DATE_MODIFIED` is seconds. Swapping them produces 1970 or a far-future date — worse than the original bug — so the convention is commented at every call site and asserted in tests. `DATE_ADDED` is never written (MediaStore-owned). A missing or zero `DATE_TAKEN` (a screenshot with no EXIF) falls back to `DATE_MODIFIED × 1000`; if neither exists the column is omitted rather than written as `0`, which renders as 1970-01-01. Values are reasserted when `IS_PENDING` clears, because some OEM implementations rewrite `DATE_MODIFIED` at that point. Reversal: trivial (drop the two helper calls). **Not covered:** albums exported before this fix still carry wrong dates. The bytes are intact so a repair pass is possible, but the export log does not persist source timestamps, so it only works where the original row still exists — a separate change, not built.

**D18 — Clustering refinement.** Grouping improved substantially once faces were aligned before embedding (D2 correction), but remained imperfect. Options: (a) tune the assign/merge thresholds; (b) add an order-independent refinement pass; (c) replace the algorithm with batch HAC/DBSCAN. → **(b).** (a) was rejected as trading one failure mode for its mirror image: lowering thresholds turns "everyone is everywhere" into "one person split into eight groups", with no principled place to stop. (c) was rejected under D5 — the online algorithm's incrementality is the point. The actual remaining defect is structural: `assign()` is a single greedy pass, so a face is locked into whichever cluster existed the moment it arrived and is never revisited as that cluster's centroid drifts. `refineAssignments()` runs up to three Lloyd-style sweeps over every face against the *final* centroids, entirely in memory off one face read and one centroid read. A hysteresis margin of 0.02 is required before a face moves; without it a face near-equidistant between two centroids flaps forever, because each move nudges both centroids. Wired into `ReclusterUseCase` only — incremental scans still get the merge pass alone. Trade-off: cost is O(iterations × faces × clusters) inside the recluster's single write transaction; a benchmark pins the read counts so a regression to per-face Room reads cannot hide inside it. Reversal: delete the call site.

**D19 — Merge chaining guard.** `mergeClose()` merged any two clusters whose *centroids* were within threshold. Centroid linkage chains: A absorbs B, the shifted A-centroid now reaches C, and two different people end up in one group through a bridge neither was ever close to. Options: (a) average-linkage check sampling member faces per candidate pair; (b) size-gated stricter threshold. → **(b).** Once either side has ≥ 8 faces the pair must clear `mergeThreshold + 0.05`. Face count is already cached and only grows within a pass, making it a free and direct signal that a cluster has absorbed others and its centroid may no longer sit near any single member. (a) was rejected because it puts Room reads inside the O(n²) pairwise loop — exactly the shape the benchmark suite exists to prevent. **Deliberately conservative, and the trade-off is asymmetric:** the guard resists merging large groups, accepting some risk of one person appearing as two in order to lower the risk of two people appearing as one. **Both constants are reasoned, not measured** — nothing here has been tuned against a real photo library, and these are the dials to turn if people start splitting into duplicates.

**D20 — Where file sizes come from.** The app needed per-photo and per-album sizes. Options: (a) add `sizeBytes` to `PhotoEntity` via an additive Room v4→v5 migration so album totals are a SQL `SUM`; (b) read from MediaStore at display time. → **(b).** (a) was the initial plan and was reversed. The cost argument for caching did not survive checking: `querySourceMetadata` already reads up to 900 sizes per cursor, so a 500-photo album is a single query, not 500. That left a migration whose only remaining effect was a correctness regression — a cached size goes stale the moment a file is replaced, while MediaStore is the source of truth. Also avoids hand-writing a schema JSON (no SDK available here to generate one) and the drift-guard round-trip that implies. Reversal: the migration remains available if a genuine need for offline size appears.

**Correction to D15 — Static analysis.** This recorded detekt as running in CI. It does not. detekt was configured, produced no report across several attempts at diagnosis, and was reverted in full rather than left in place as config that reads as coverage without providing it. AGP lint is the only static analysis actually running.

**D21 — minSdk raised 26 → 29, superseding D14.** D14 recorded minSdk 26, but export was broken below API 29 and always had been: the copy path writes `RELATIVE_PATH` and `IS_PENDING` into MediaStore, both API 29+, and MediaStore rejects an unknown column by throwing. On API 26–28 exporting an album failed outright. Options: (a) leave it and let export fail on those devices; (b) add a legacy write path; (c) raise minSdk to 29. → **(c).** (b) is not available at any price this app is willing to pay — writing into `Pictures/` before scoped storage requires `WRITE_EXTERNAL_STORAGE`, which FaceAlbum deliberately never requests and whose absence is load-bearing for the privacy claims in `08-privacy-security.md`. (a) was rejected because shipping a build that advertises support for a platform where the core feature cannot work is the bug, not a mitigation for it. The real defect was the mismatch between the declared floor and the architecture, which has been scoped-storage-only since D9; 29 is where that architecture actually starts working. **Cost, stated plainly:** Android 8.0/8.1 devices can no longer install the app. Reversal: dropping the floor back requires a legacy write path and the permission that goes with it, so this is effectively one-way. Follow-on cleanup: the conditional `RELATIVE_PATH` projection in `queryPhotoDetails` was removed, since the column is now always present.
